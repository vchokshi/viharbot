# ADR-009: Persistent, governed agent memory

**Status: Proposed. Amended 2026-11-10 (founder decision): PostgreSQL is the memory backend in every environment; see "Amendment: PostgreSQL everywhere".** Nothing here is implemented or provisioned. It is intended to satisfy the memory design that issue #40 depends on (cited there as "ADR-003"), and to support the isolation and poisoning tests in #48. The founder confirms the numbering and still has to accept this ADR as amended.

## Context

Verified in the repository:

- `remember()` appends `{timestamp, request_id, result}` to `$MEMORY_DIR/<agent>/memory.jsonl` (`memory.py`). Callers are the research, security, specialist and Sage agents; Pixel keeps deck state as files under `MEMORY_DIR/pixel`.
- Nothing reads these files back (`docs/memory-architecture.md`). On DigitalOcean `MEMORY_DIR` is `/tmp/viharbot-memory`, so records are ephemeral. Compose uses bind mounts or named volumes.
- The constitution (Article VIII) requires a defined memory scope per agent, governed cross-scope access, provenance, validation before anything becomes institutional knowledge, and that confidential client details never flow into global memory.
- There is no read path, no metadata, no authorization, no versioning, no idempotency (a retry can append a duplicate), no promotion workflow, and no engagement or principal key. Memory is partitioned only by an agent string.
- `AGENTS.md` says each agent keeps independent memory, to start with simple isolated storage, and not to add a database without a concrete need.

## Decision

**One PostgreSQL database behind a small memory API service, in every environment** (a container locally, DigitalOcean Managed PostgreSQL for Stage, Amazon RDS for PostgreSQL for Production; see Amendment). Semantic search, AgentCore Memory, OpenSearch, pgvector and Bedrock Knowledge Bases are deferred until recall quality is shown to be insufficient. *Superseded by the amendment: the original decision was one DynamoDB table with S3 for large bodies, for Production only. The DynamoDB text below is kept as the historical design and as the source of the guarantees the PostgreSQL mapping must reproduce.*

## Amendment: PostgreSQL everywhere (founder decision, 2026-11-10)

**Why.** Stage runs on DigitalOcean, which has no DynamoDB, and App Platform's local disk is not persistent (DigitalOcean's limits page recommends Managed Databases or Spaces for durable state). The DynamoDB design left Stage without a backend that could honor the same contract, so every guard rule would have been implemented and tested twice. PostgreSQL exists as a container for local development, as DigitalOcean Managed PostgreSQL for Stage and as RDS for PostgreSQL in AWS, with real transactions in all three (`docs/datastore-platform.md`). One contract and one conformance suite now cover every environment.

**What changes**

| Area | Before | After |
|---|---|---|
| Backend | DynamoDB (Production), unchosen (Stage) | PostgreSQL in all environments |
| Local | not specified | PostgreSQL container on the private Compose network |
| Stage | open | DigitalOcean Managed PostgreSQL |
| Production | DynamoDB + S3 | RDS for PostgreSQL (Aurora PostgreSQL is not excluded; not chosen here) |
| Bodies | S3 object per generation, with leases, epochs and an orphan sweep | stored in the database row, in the same transaction as the version, until a measured need for object storage exists |
| Authorization reads | DynamoDB `ConsistentRead=true` | read from the primary only, inside the transaction |

**Platform policy (founder, 2026-11-10).** DynamoDB remains an approved store for features that need it, provided they have a working rollout in both DigitalOcean and AWS, and GCP is an approved cloud (Cloud SQL for PostgreSQL is the matching backend there; nothing is provisioned). Neither reopens this decision: memory stays on PostgreSQL. See `docs/datastore-platform.md`.

**What does not change.** The contract in this ADR: record metadata, retrieval and write authorization, deny by default, the promotion rules, the deferral of cross-scope promotion, read-time retention, `retire` versus `erase`, tombstones, idempotency, and the memory service as the only holder of data-plane credentials. Authorization stays in the memory service, never in the database. Database roles and row-level security may be added as defense in depth but are not the control.

### PostgreSQL mapping of the guard rules

These are the intended mechanics. They use standard PostgreSQL behavior (transactions, row locks, unique constraints, conditional `UPDATE`), which this change did **not** re-verify against the PostgreSQL or provider documentation; the conformance suite must prove each one.

| Required guarantee (DynamoDB term in the text below) | PostgreSQL mechanism |
|---|---|
| Atomic multi-item write (`TransactWriteItems`) | One database transaction per mutation |
| `current.rev == expected_rev` and `lifecycle == active` (conditional update) | `UPDATE ... SET rev = rev + 1 ... WHERE id = $1 AND rev = $2 AND lifecycle = 'active'`; zero rows updated means the writer lost and must re-read and re-authorize |
| Engagement open check (G2) | The transaction takes a shared lock (`SELECT ... FOR SHARE`) on the `engagement` row and requires `state = 'open'`; closure takes an exclusive lock, so a write and a closure serialize |
| Idempotency items (`idem#`) | A unique constraint on (principal, record, idempotency key) storing the original result; a retry returns it |
| Tombstones (`tombstone#`) | A tombstone table with a unique constraint; create refuses a tombstoned id or key |
| Erase write barrier | One transaction sets `lifecycle = 'erased'` and inserts the erase row, conditioned on `lifecycle <> 'erased'` and not on `rev`, so it cannot lose to a racing writer |
| Strongly consistent authorization read | Read `current` on the primary, in the same transaction as the write; never from a read replica or standby |
| Body generations, leases, `lease_epoch`, `max_lease_expiry`, orphan sweep | **Not needed** while bodies live in the row; they return only if object storage is added later and must then be re-derived and re-tested |
| Physical erasure | `DELETE` of the record's rows inside the erase-completion transaction, followed by the tombstone insert |

Isolation level (for example `READ COMMITTED` with the explicit row locks above, or `SERIALIZABLE` with retry on serialization failure) is **not decided** here; it is chosen by the conformance suite and recorded in the implementation PR.

**Limits stated plainly.**
- A read replica or standby can lag, so authorization decisions must never use one. DigitalOcean Managed PostgreSQL offers standby and read-only nodes; the memory service must connect to the primary only.
- Managed backups keep copies of erased data. DigitalOcean lists daily point-in-time backups for PostgreSQL; an `erase` therefore still does not claim to remove backup copies, and backup retention remains an open decision.
- DigitalOcean announced plan changes for Standard Edition PostgreSQL (limits above 4 GiB RAM and on standby or read-only nodes for new clusters from 15 and 30 November 2026). Check the current plan before choosing a Stage size.
- Cost is not estimated here. A managed PostgreSQL instance has a standing monthly cost on both providers, unlike DynamoDB on-demand; provisioning needs the approval already required by `AGENTS.md`, and a Stage change is a cost change to report before promotion.

**Conformance.** The same contract and interleaving tests (below) run against the local PostgreSQL container and against the Stage and Production instances before each is adopted. The transaction-shape check applies to SQL statements instead of `TransactWriteItems`: every mutation's statements and the locks it takes are listed and tested.

### Environment placement (founder decision, 2026-11-03; backend superseded by the amendment above)

The founder decided: **Stage memory is kept in DigitalOcean; Production memory is kept in AWS.** The memory **contract** is the same in both environments: record metadata, write and read authorization, versioning and supersession, retention, retirement and erasure semantics, audit, and the guard rules under Consistency rules. Only the backend differs.

| Environment | Backend | Status |
|---|---|---|
| Local | PostgreSQL container (Docker Compose, private network) | Amended design; not yet added to Compose |
| Production | AWS: RDS for PostgreSQL (originally DynamoDB with S3) | Amended design; not provisioned, and no AWS resource is created without explicit approval |
| Stage | DigitalOcean Managed PostgreSQL (originally open) | Amended design; not provisioned; a cost change to report before promotion |

Not decided or verified by this ADR (items marked *resolved* were open before the amendment):

- **Which DigitalOcean store holds Stage memory.** *Resolved by the amendment: Managed PostgreSQL.* DigitalOcean's documentation lists it as a managed engine; plan sizes, prices and the plan-limit changes noted above are not verified here.
- **Persistence on App Platform.** Per `docs/memory-architecture.md` and `deploy/digitalocean/app.yaml`, App Platform containers write memory to an ephemeral disk (`/tmp/viharbot-memory`), so a container-local store would lose data on redeploy or restart. Any container-based Stage store needs a verified persistence answer from official DigitalOcean documentation first. That documentation has not been fetched for this change, so it is an open question, not a finding.
- **Atomicity of the Stage backend.** The guard rules rely on atomic multi-row conditional writes, reads that cannot be stale, and a transaction that fences stale writers. The amendment maps these to PostgreSQL transactions, conditional updates and row locks, identical in all environments; the conformance suite must prove it on each instance before it is adopted. If it cannot, the guard rules cannot be claimed for that environment.
- **Cross-environment data movement.** Whether Stage data may ever reach Production, or Production data reach Stage, is not decided. Until it is, neither direction is allowed, and the engagement and institutional tiers keep separate namespaces per environment.

**The consistency rules below were written in DynamoDB terms and are retained as the historical design.** They state the required semantics; the amendment's PostgreSQL mapping replaces the DynamoDB mechanics wherever the two differ, and the same interleaving tests apply to the PostgreSQL implementation.

### Taxonomy

| Type | Store (amended: PostgreSQL tables in every environment; DynamoDB wording is historical) | Scope key | Lifecycle |
|---|---|---|---|

| Engagement | DynamoDB, large bodies in S3 | `eng#<id>` | Retained per engagement; closure is governed by an `engagement#<id>` authority item (open, closing, closed) and retires every record (no longer served, history kept to `retention_until`); erased only on consent withdrawal or another policy-named reason |
| Institutional | DynamoDB, `validated` only | `inst#<topic>` | Written only after human or reviewer approval; versioned and retired (or erased under policy), never overwritten |

### Record metadata

`pk`, `sk`, `version`, `rev`, `owner`, `agent_scope`, `engagement_scope`, `classification`, `authorized_principals[]`, `provenance{source, author, request_id}`, `retention_until`, `validated_at`, `validated_by`, `status` (workflow: `observed`, `proposed`, `validated`, `superseded`), `lifecycle` (`active`, `retired`, `erased`), `supersedes`, `idempotency_key`, `body_ref` (which carries the body generation). The record-level policy fields (`authorized_principals`, `classification`, `retention_until`, `lifecycle`) and `rev` live on the `current` item and are authoritative; copies on `v#<n>` items are history only and are never used to decide access. Engagement closure is authoritative on the separate `engagement#<id>` item (see Consistency rules). `version` counts content versions; `rev` is a monotonic counter advanced by **every** mutation of `current`: each content write, policy change, retire, erase and engagement-closure retirement.

### Authorization at the retrieval boundary

The memory service filters before anything is returned. Prompts never enforce access.

1. The caller authenticates under ADR-006. The service derives principal, agent and engagement scope from the verified token, and the caller cannot assert them.
2. Every query is built from the derived scope keys, and each returned item must also pass an ACL check (the principal is in `authorized_principals` and the scope matches).
3. If semantic search is added later, it must pre-filter on the authorized keys, or over-fetch and post-filter. Unfiltered hits are never returned.
4. Returned content is wrapped as data with its provenance and a "not instructions" marker.
5. Only `validated` items are served from the institutional tier.
6. Every read and write is audited. Logs carry identifiers, never content.

### Write-side authorization

Retrieval filtering alone does not stop an authorized writer from assigning another engagement, widening access or forging validation. Every mutating operation is **deny by default** and checked by the service from the verified token and policy, never from caller-supplied fields.

| Operation | Rule |
|---|---|
| Create or update a record | Allowed only inside the caller's own scope. `owner`, `agent_scope` and `engagement_scope` are **derived server-side** from the token. A request that names a different scope or owner is refused. |
| `classification` | The caller may set it only at or below its classification ceiling, and may raise it freely but never lower it. Lowering needs the owner or a policy-named reviewer. |
| `authorized_principals` | Defaults from policy for the scope. Widening it needs a principal named in policy as allowed to grant access to that scope; a writer cannot add itself or a peer. |
| Validation fields (`status`, `validated_at`, `validated_by`) | Settable only by the promotion operation. A normal write that supplies them is refused. |
| Promotion (`observed` or `proposed` to `validated`) | Needs a principal named in a **reviewer policy** for that tier and type, who is not the writer. Being a different principal is necessary, not sufficient. Reviewer eligibility is configuration reviewed in the repository, never inferred. |
| Supersede, `retire`, `erase` | Owner or a policy-named principal only; each is audited. `retire` and `erase` are different operations (see Retention, retirement and erasure). |
| Close an engagement | Only a principal named in an **engagement-closure policy** for that engagement (reviewed in the repository, never inferred, never the caller's own assertion). Audited with identifiers and reason. See Engagement closure under Consistency rules. |

Required negative tests: forged scope, owner or engagement; classification lowered by a writer; ACL widened by a non-authorized writer; validation fields in an ordinary write; promotion by the writer, by an ineligible principal, and by a reviewer of the wrong tier; retirement or erasure by an unrelated principal; engagement closure by an unauthorized principal.

### Historical versions follow the record's current access policy

Authorization for a record is decided from the policy fields on the record-level `current` item (`authorized_principals`, `classification`, `retention_until`, `lifecycle`) and from the engagement's authority item, **never from the access metadata stored on an older version**. A policy change (revoking a principal, raising `classification`) is one conditional update of `current` that also advances `rev`, so it applies to every version and every body of that record from the moment it commits, and any writer holding an earlier `rev` fails. Engagement closure is a state change on `engagement#<id>` followed by retiring each record (see Engagement closure), not a single update of `current`. Old versions are readable only by principals the current policy allows, and a body object is never reachable except through the service: S3 buckets are private, there are no presigned URLs and no direct object access for agents.

**Read-consistency contract (recommended).** Every authorization decision, for any version or body, reads `current` (and, for engagement records, the `engagement#<id>` item) with a **strongly consistent read** (DynamoDB `ConsistentRead=true`), and authorization state is **never cached** in the service, an agent or a proxy. A read that starts after a policy change commits therefore sees the change; a read already past its policy check when the change commits may complete, and that bounded in-flight window is the revocation boundary. Cost, stated as ASSUMED from DynamoDB's published model and to be confirmed in the AWS calculator: a strongly consistent read uses twice the read capacity of an eventually consistent one, and the service needs one or two such reads per request at this low volume, so the extra cost is small. The alternative is a cache with an explicit, bounded staleness window (a stated number of seconds) and an invalidation rule on every policy-changing write; during that window revocation is not immediate, and the ADR would then have to say so wherever it promises revocation. This ADR recommends the strongly consistent read with no cache, and the founder decides.

Tests: after access is revoked, the very next read of the record, an older version and its S3 body is refused; after classification is raised, an older, lower-classified version is refused to a principal below the new ceiling; once closure sets `closing` the next ordinary read is refused, before any record has been retired; a read issued after a policy change never uses a cached or eventually consistent copy (the test fixture serves a stale `current` to any non-consistent read and the service must still refuse); if a cache is ever introduced, a read after the staleness window or after invalidation does not use the stale entry.

### Promotion across scopes is deferred and denied

Promotion in the table above moves a record's status inside the scope it already lives in. **Moving engagement-derived content into institutional memory is a different, cross-scope operation, and this ADR does not define it.** Until a follow-up ADR does, any attempt to publish engagement or agent content into the institutional tier is denied. That follow-up would need authorized source and destination scopes, a confidentiality review or redaction step before publication (constitution 8.4 forbids confidential client details entering global memory), destination ACL checks, and preserved provenance. Required negative test: engagement content marked confidential cannot enter institutional memory by any operation.

### Retention, retirement and erasure

`retention_until` and engagement closure are enforced **at read time**, independent of DynamoDB's asynchronous TTL (which only reclaims storage some time after expiry, so an expired record can remain queryable). The service refuses to return an expired record, and refuses ordinary retrieval of any record whose engagement is not `open` (see Engagement closure; the history-read rule below still applies after closure until `retention_until`). Two distinct operations end a record's life:

- **`retire`** stops normal serving: the record no longer appears in ordinary retrieval and `current.lifecycle` becomes `retired`, in one conditional update that requires `lifecycle == active` and advances `rev`. History is kept: old versions and **all bodies are retained until `retention_until`**, readable only by principals the current policy allows for history. When `retention_until` passes, the record is expired; before deleting any body, the delete job applies the retire update to a still-`active` expired record (advancing `rev`), so the guards below close the generation set for expiry exactly as for erase, and its bodies are then deleted by the delete job below. Engagement closure retires that engagement's records. Because `rev` advanced and `lifecycle` is no longer `active`, a writer holding an earlier `rev` cannot publish to a retired record.
- **`erase`** is for consent withdrawal and similar cases, requested by the owner or a policy-named principal, audited with identifiers and reason, never content. It overrides retention and has two stages. **Logical erasure is immediate:** one conditional update of `current` (condition `lifecycle != erased`, deliberately not conditioned on `rev`, so it cannot lose to a racing writer) sets `lifecycle` to `erased` and advances `rev`, in the same transaction that puts the durable `erase` item (`attribute_not_exists`, so there is never an erased record without its erase item). This is the write barrier: every publishing transaction conditions on `current.rev == expected_rev` **and** `current.lifecycle == active`, so a writer that read before the erase fails on `rev`, and a writer that reads after it sees `erased`, is refused by the service and would also fail the guard. Every read of any version or body is refused from that point. **Physical deletion is eventual:** a durable `erase#<record>` item lists every version and body generation and tracks per-object progress, and the delete job (idempotent, retried) removes bodies through the generation-fenced `deleting` state below and then the version items; `current` is deleted only in the erase completion transaction, which writes the `tombstone#<id>` (see Consistency rules). The service reports `access stopped` when the first stage commits and `physically deleted` only when the job has verified that every listed object and item is gone and the erasure completion boundary under Consistency rules has passed; it never reports completion earlier.

Body deletion (after `erase`, or after `retention_until` for a retired or expired record) runs as an idempotent delete job with retries, and an orphan sweep finds bodies with no live record (protocol under Consistency rules). Whether backups and point-in-time recovery are enabled, and for how long, is an open decision; until it is made they are off and the gap is stated. Because erasure of backups is not covered, an `erase` does not claim to remove backup copies. Tests: an expired-but-present record is not returned; a closed engagement's records are not returned by ordinary retrieval; a retired record is not in ordinary retrieval, its history and bodies remain readable to authorized principals until `retention_until`, and its bodies are deleted after it; an erased record is refused on the very next read and write while deletion is still pending, including a writer that read the record before the erase and a writer that reads after it (interleaving tests in Consistency rules); the job's retry after a mid-way failure finishes the deletion; `physically deleted` is reported only after every version and body is verified gone; the erase is audited; `erase` by an unrelated principal is refused; an orphaned body is found by the sweep.

### Consistency rules

> **Amended 2026-11-10:** this section describes the original DynamoDB mechanics. Read it for the guarantees (G1, G2, `rev` fencing, tombstones, idempotency, the erase barrier); implement them with the PostgreSQL mapping in the amendment. The body-generation, lease and orphan-sweep protocol below applies only if object storage is added later.

A write is one atomic **DynamoDB** transaction (`TransactWriteItems`, which supports Put, Update, Delete and ConditionCheck actions on several items, including items with different partition keys in one table; conditional writes and strongly consistent reads are likewise documented DynamoDB features, not re-verified in this change, and no transaction size limit is relied on), so revision checks, supersession and de-duplication of the metadata cannot be partly applied. The atomicity claim covers DynamoDB only; S3 bodies follow the ordering below. Layout, per logical record `pk = <scope>#<record_id>`, plus one authority partition per engagement:

| Item (`sk`) | Contents |
|---|---|
| `v#<n>` | An immutable version: body or `body_ref`, metadata, `status` |
| `current` | The current version number, `rev`, `lifecycle`, workflow `status`, and the authoritative record-level policy: `authorized_principals`, `classification`, `retention_until`. Authorization reads this item with a strongly consistent read |
| `idem#<key>` | The result of an earlier write with this idempotency key (the version it created and the body generation it published); the key is scoped to the principal and the record, for example `request_id#kind` |
| `bodyres#<hash of idem key>` | Durable reservation record mapping the idempotency key to a body generation `gen` (see Bodies below) |
| `body#<gen>` | Lifecycle item for one body generation: `state` (`reserved`, `referenced`, `deleting`, `deleted`), `lease_expiry` (the writer's upload lease), `lease_epoch` (fencing token), `owner` and `claim_expiry` (the deletion worker's claim, a separate field that never extends upload eligibility) |
| `lease` | Record-level item holding `max_lease_expiry`, a monotonically non-decreasing value: the latest upload `lease_expiry` ever granted for any generation of the record. Written in the same transaction as every upload-lease grant or renewal and never lowered or deleted before erase completion |
| `erase` | Created in the same transaction that commits erase (see Retention, retirement and erasure): `status` (`pending`, `physically_deleted`), the object list and per-object progress, and a `max_lease_expiry` snapshot copied from `lease` once erase has committed |
| `engagement#<id>` / `state` | Engagement authority item (its own partition): `status` (`open`, `closing`, `closed`), `epoch`, `closed_by`, timestamps. Read with strong consistency |
| `engagement#<id>` / `rec#<record_id>` | Registry entry written in the same transaction that creates each engagement record, so the set of records is enumerable by a strongly consistent Query without a secondary index |

- **One action per item (rule).** DynamoDB `TransactWriteItems` does not allow more than one action on the same item in one transaction (documented DynamoDB behavior, not re-verified in this change; to be confirmed against DynamoDB Local). **At most one action per item per transaction** therefore applies to every transaction in this ADR. A guard on an item that the transaction also writes is expressed as the `ConditionExpression` of that item's own Update, Put or Delete. A standalone `ConditionCheck` is used only on an item that the transaction does not otherwise write.
- **Write path:** `TransactWriteItems` containing exactly these actions, one per item: (a) an **Update of `current`** to `n+1` that advances `rev`, whose `ConditionExpression` is `rev == expected_rev` **and** `lifecycle == active` (an explicit non-retired, non-erased guard; the version the caller read is implied by `rev` because every write advances it), (b) for an engagement record, a `ConditionCheck` that `engagement#<id>`/`state` has `status == open` (that item is not written here), (c) a put of `v#<n+1>`, (d) an update of `v#<n>` to `superseded`, (e) the update of `body#<gen>` to `referenced` whose own `ConditionExpression` is the body-state guard below, and (f) a put of `idem#<key>` with `attribute_not_exists`. There is no separate ConditionCheck on `current` or `body#<gen>`. **Content publication and policy maintenance have different guards.** Content writes and promotion require `lifecycle == active` and the engagement `open` check. Authorized policy updates (ACL, classification) are separate transactions that require `rev == expected_rev` and `lifecycle != erased`, and do **not** require `active` or an `open` engagement, so access to retained history can still be narrowed on a `retired` record or after engagement closure. Every policy update advances `rev` and leaves `lifecycle` unchanged, so an in-flight content write that read before it fails and must re-read and re-authorize. On a `retired` record a policy update may only narrow access (revoke a principal, raise `classification`); widening access to retired history is refused by default. Retire and erase advance `rev` as described above. Either all of it commits or none does, so there is never more than one current version and the history is never inconsistent.
- **Bodies in S3 are immutable, never reuse a key, and are uploaded first.** Every body write gets a unique, never-reused **generation ID** (`gen`, a random identifier such as a UUID or ULID) assigned when its lifecycle item is reserved. The object key is `bodies/<record>/<gen>`, uploaded with server-side encryption and no overwrite, and only then does the transaction publish a `body_ref` naming that `gen`. Because a key is used for exactly one generation, a deleted generation is never republished and no later write can land on a key an earlier worker still intends to delete. A `body_ref` is never committed before its object exists. If the upload succeeds but the transaction fails, the object is an unreferenced orphan.
- **Body-lifecycle guard rule (normative).** *Every body-lifecycle mutation carries the lifecycle, rev and engagement guards.* A writer-side mutation is any transaction that creates a generation, replaces a generation, grants or renews an upload lease, or publishes a body. Each one includes, in the same `TransactWriteItems`: (G1) the condition that `current.lifecycle == active` and `current.rev == the rev the service authorized against`, attached as the `ConditionExpression` of the Update of `current` where the transaction already updates `current` (publish), and as a standalone `ConditionCheck` on `current` in every other writer-side transaction (reservation, renewal, replacement, takeover), none of which writes `current`; (G2) for an engagement record, a `ConditionCheck` that `engagement#<id>`/`state` has `status == open`; and (G3) where it grants or renews a lease, an update of `lease` setting `max_lease_expiry` to the new `lease_expiry`, conditioned on `attribute_not_exists(max_lease_expiry) OR max_lease_expiry <= :new` (monotonic; a failed condition means a larger value already exists, and the writer re-reads and retries). A deletion-side mutation moves a generation only toward deletion and carries the state and epoch conditions of its own transition; where it deletes a `referenced` or unexpired `reserved` generation it also carries a standalone `ConditionCheck` on `current` (which that transaction does not write) that `lifecycle` is `erased`, or `retired` with expiry passed. Any body-state condition is attached to the Update or Put of that `body#<gen>` item itself, never as a second action on it. Deletion-side mutations never extend an upload lease and never change `max_lease_expiry`. Time values in conditions are supplied by the service from its clock, because DynamoDB condition expressions have no server-side clock; bounded clock skew is an ASSUMED property to be tested. Because erase, retire and engagement `closing` each change a guarded item, no writer-side transaction can commit after any of them, whether it is a first attempt, a retry, a replacement, a renewal or a lease takeover. The table lists every body-lifecycle and erase transaction, with the single action on each item, so that no path is omitted and none names two actions on one item:

  | Transaction | Actions (one per item) | G1 lifecycle and rev | G2 engagement open | Body-item condition | `max_lease_expiry` |
  |---|---|---|---|---|---|
  | Initial reservation | CC `current`; CC engagement `state`; Put `body#<gen>`; Put `bodyres#`; Update `lease` | standalone CC: `active`, authorized `rev` | CC | on the Put: `attribute_not_exists` (also on the `bodyres#` Put) | raised |
  | Lease renewal (retry, unexpired) | CC `current`; CC engagement `state`; Update `body#<gen>`; Update `lease` | standalone CC: `active`, authorized `rev` | CC | on the Update: `reserved`, `lease_epoch` held, lease unexpired | raised |
  | Expired-lease takeover (retry of a `reserved` generation) | CC `current`; CC engagement `state`; Update `body#<gen>`; Update `lease` | standalone CC: `active`, authorized `rev` | CC | on the Update: `reserved`, `lease_epoch` held, lease expired; advances `lease_epoch`, sets new `lease_expiry` | raised |

  CC means `ConditionCheck`. The first publish is the normal Publish minus the `v#<n>` supersession update, because no earlier version exists. In every row each item appears at most once. A policy update advances `rev`, so it also fails an in-flight writer-side transaction; that writer re-reads, re-authorizes and retries, and an unrenewed lease simply expires.
- **Creation sequence (how version 1 of an S3-backed record comes to exist).** Body reservation requires an existing `active` `current`, so creation is three steps, chosen over reserving the body inside the create transaction because it keeps one reservation, retry and takeover path for every body and keeps the create transaction free of leases and `lease` writes. (1) **Create** the record's `current` (active, `rev` 0, `current_version` 0, no body, draft) in the record-create transaction above, with its `rec#` registry entry and the engagement-open check for engagement records; `idem#<key>#create` makes a retry of creation return the original record. (2) Run the normal **initial reservation** against that `current` at the `rev` the writer read (G1 to G3 apply unchanged; the `lease` item is created by its first Update). (3) Upload, then **first publish** as in the table. An authorized policy update on the empty record advances `rev`; the first publish then fails its `rev` condition, and the writer re-reads, re-authorizes and retries at the new `rev`, so an update never blocks first publication permanently. A crash after step 1 leaves a harmless empty active record (no version, no body, not served as content), which a retry of the write continues from step 2 and which the closure sweep or retention retires like any other. A create that loses to engagement `closing` fails its `open` check and a record already created is retired by the sweep, so an empty record never survives in a `closed` engagement. For seeding or tests, versions may be created **synthetically** through this same contract (clearly labelled test or lab data in metadata, written by the same transactions with the same guards); direct table writes that skip the guards are not permitted, including in fixtures that claim to test the guards.
- **Reservation and idempotent retry.** The writer first runs one transaction carrying G1 and G2 that puts `body#<gen>` as `reserved` (fresh lease, `lease_epoch = 1`) with `attribute_not_exists`, puts `bodyres#<hash of idem key>` recording `gen` with `attribute_not_exists`, and raises `max_lease_expiry` (G3), so no reservation can be created once erase or retire has committed. A retry after a lost response (same idempotency key) finds `bodyres#<hash>` and reuses the recorded `gen` instead of computing a new key: if `idem#<key>` exists it returns the original result; if `body#<gen>` is `reserved` with an unexpired lease it renews the lease in one transaction carrying G1 to G3 and a condition on `lease_epoch`, then continues; if `body#<gen>` is `reserved` with an **expired** lease (the previous writer crashed after reserving, possibly before uploading, so there may be no S3 object for the sweep to find), the retry **takes the lease by a fenced takeover on the same generation**: one transaction carrying G1 to G3 whose Update of `body#<gen>` requires `reserved`, the epoch the retry read and an expired lease, advances `lease_epoch`, sets a fresh `lease_expiry`, and raises `max_lease_expiry`; it then uploads under the **same** `gen` (no overwrite) and continues to publish. If the object already exists (a crash after upload and before publish), the retry confirms it with `HeadObject`, verifies it against a content hash recorded on `body#<gen>` at reservation (ASSUMED: SHA-256 of the body), and publishes if it matches; on a mismatch it abandons that generation and takes the replacement path below. Reuse of the same generation was chosen over abandoning it to the sweep because the sweep is object-oriented and cannot see a reservation with no object (a retry would otherwise be stuck), and reuse creates no extra orphan; the takeover's epoch advance fences the crashed writer if it wakes later. A sweeper racing the takeover contends on the same item: exactly one of the takeover and the sweep claim passes the `reserved`, expired and epoch conditions, and if the sweep wins the retry next sees `deleting` and takes the replacement path. If `body#<gen>` is `deleting` or gone (the lease expired and the sweep claimed it), it starts a fresh generation by one transaction carrying G1 to G3 that creates the new `body#<gen2>` and updates `bodyres#<hash>` from `gen` to `gen2` with a condition that it still names `gen`. A retry that observed `deleting` or gone before an erase commits and executes afterwards fails G1, creates no generation and extends no lease. The generation is therefore recorded durably in the lifecycle item, in the reservation record and, once published, in the idempotency result.
- **Sweep, deletion ownership and fencing.** Writers and the sweep contend atomically on `body#<gen>`; S3 provides no synchronization with DynamoDB, so DynamoDB is the only arbiter. (1) Writer: upload to `bodies/<record>/<gen>` (no overwrite) and `HeadObject` to confirm it. (2) The publishing transaction adds a condition that `body#<gen>` is `reserved`, `lease_epoch` equals the writer's epoch and the lease is unexpired, and updates it to `referenced`. (3) Sweep: for an object older than a grace period longer than the maximum write time, a conditional update moves `body#<gen>` to `deleting` only if it is `reserved` with an expired lease (or absent, created as `deleting`), never if `referenced`, and in the same update advances `lease_epoch` and records the sweeper as `owner` with its own `claim_expiry` (not the upload `lease_expiry`, and `max_lease_expiry` is untouched). That epoch is a **fencing token**: every later conditional update by a worker (completing, removing the item) must name the `gen` and its remembered `lease_epoch`, and fails if another worker has since advanced it. (4) A second sweeper that finds `deleting` with an expired `claim_expiry` may take it over only by a conditional update that advances `lease_epoch`, after which the first worker's late updates fail. (5) The S3 `DeleteObject` call itself cannot carry the epoch, but it is safe because it addresses only `bodies/<record>/<gen>`: once `deleting` commits, step 2 can never commit for that `gen`, no writer ever republishes it, and a late delete hits only an object that is already dead. A new write for the same record or idempotency key uses a different `gen`, so a paused worker's delayed delete cannot affect it. (6) After the delete is confirmed, the owner removes `body#<gen>` with a condition on `state == deleting` and its `lease_epoch`. Bodies of retired-and-expired or erased records are deleted through the same path: a conditional transaction moves `body#<gen>` from `referenced` to `deleting` only together with a `ConditionCheck` that the record's `current.lifecycle` is `erased`, or is `retired` or expired with `retention_until` passed. **Erasure completion boundary.** Because every writer-side transaction (reservation, replacement, renewal, publish) is fenced by `current.lifecycle` under the guard rule above, the set of `body#<gen>` items and the value of `max_lease_expiry` are both closed once the erase commits, and the delete job enumerates the generations with a strongly consistent Query on the record partition (plus the `v#` items). For erase, the job may move a `reserved` generation to `deleting` without waiting for its lease to expire, under a `ConditionCheck` that `lifecycle == erased`, and leaves a `deleted` tombstone instead of removing the item until the erase is complete. S3 cannot stop a writer that was paused after reserving from uploading later, so the protocol bounds it: a writer must not begin an upload unless its remaining lease exceeds the maximum upload time and must enforce that deadline on the request (a bounded-worker assumption, ASSUMED and to be tested, not guaranteed by S3). The service reports `physically deleted` only when (1) every listed item and generation is deleted, (2) the current time exceeds `max_lease_expiry` (read from `lease`, snapshotted into `erase` after the erase commit; monotonic, so it covers every generation ever leased, including replaced, deleted and taken-over ones, because no lease transaction can lower it and none can raise it after erase) plus a clock-skew allowance (ASSUMED, to be set), where the writer's upload deadline lies inside its lease, and (3) a final reconciliation listing of the `bodies/<record>/` prefix is empty (S3 listing consistency to be confirmed against current AWS documentation before relying on it). Completion is one conditional update of `erase` to `physically_deleted`, refused unless every generation is `deleted`, the time condition holds and the final listing was empty; if it is refused the status stays `pending`. A lease holder paused past its expiry that wakes later cannot commit any renewal, replacement or publish (G1 fails once erase has committed, and the lease and epoch conditions fail regardless), so only a late S3 upload is possible, which the bounded-worker assumption, the final listing and the orphan sweep address. An object that still appears later, for example from a worker that violated the bound, is removed by the orphan sweep, which keeps covering the prefixes of erased records; that residual risk is stated, not eliminated.
  Crash recovery: a writer that dies leaves a `reserved` item whose lease expires, after which either the sweep may claim it (if an object exists and is older than the grace period) or the writer's retry takes it over under the same generation as described under Reservation; a sweeper that dies after `deleting` is resumed by another sweeper through the takeover in (4). Lease length must exceed the maximum write time (ASSUMED value to be set and tested).
- **Record identity is never reused (normative).** Record ids are generated by the service at creation as unique, non-recyclable identifiers (ULID or UUIDv7); a caller never supplies an id as a create key. Physical deletion would otherwise remove `current` and let a new record take its place, bypassing the erase barrier and letting old references, `idem#` results or leases attach to it. So erase completion writes a never-deleted `tombstone#<id>` in the same transaction that deletes `current`, and, where a caller-chosen business key maps to a record, a never-deleted `tombstone#key#<key>` too; create refuses a tombstoned id or key. A tombstone holds only ids and timestamps (no content), survives physical deletion and is retained indefinitely (it is tiny; any shorter retention would need a separate ADR). `idem#` and `lease` items are scoped by record id, so a new record's distinct id cannot match them. This is a design commitment, not implemented or verified.
- **Racing writers:** exactly one transaction passes the `rev` condition; the other fails, re-reads and retries or reports a conflict. A writer whose read predates any lifecycle or policy mutation also fails.
- **Engagement closure.** Closure has its own authority and completion barrier. The `engagement#<id>`/`state` item holds `status` (`open`, `closing`, `closed`) and an `epoch` that advances on every transition; every create, write and read path reads it with a strongly consistent read. Only a principal named in the engagement-closure policy may close, derived from the verified token and audited with identifiers and reason. (1) **Begin:** a conditional update `open` to `closing` (advancing `epoch`, recording the closer). From the moment it commits, every record create and every write transaction fails its `ConditionCheck` that the engagement is `open`, and ordinary and history reads of the engagement's records are refused. (2) **Sweep:** a worker enumerates the registry (`rec#` entries, strongly consistent Query) and retires every record whose `lifecycle` is `active`, each by the retire update (advancing `rev`), retrying on conflict; workers carry the `epoch` they observed and fail if it changed. (3) **Verify, then complete:** a verification pass re-queries the registry and strongly re-reads every `current`; only if none is `active` does a conditional update `closing` to `closed` (condition on `epoch`) commit. If any record is still active or the pass cannot complete, the engagement stays `closing`, which keeps creates and writes blocked, and the service reports closure as incomplete; it never reports `closed` earlier. Because creates are blocked before the sweep begins and each create writes its registry entry in the same transaction, the registry is complete once `closing` commits. After `closed`, history reads follow the existing rule until `retention_until`. Reopening is not defined here. The closing principals and policy are unresolved.
- **Retry after a committed write whose response was lost:** the retry's `idem#<key>` put fails its condition, so nothing is written twice; the service reads that item and returns the original result.
- **Supersession:** never overwrite; old versions stay readable by authorized principals for history until `retention_until`, including after `retire`. Only `erase` removes history early.
- **Promotion:** `observed` or `proposed` to `validated` needs a reviewer principal different from the writer. No code path promotes automatically (constitution 8.3).
- **Failover:** state is keyed by the logical agent and engagement, never by instance.
- **Transaction-shape check (required review check and test).** For every transaction in the table above, a fixture builds the exact `TransactWriteItems` request and asserts that no two actions share the same table and key (the rule: at most one action per item per transaction), that every guard named in the table is present either in the ConditionExpression of that item's own action or as a standalone ConditionCheck on an item with no other action, and that a standalone ConditionCheck on `current` never appears in a transaction that also updates or puts `current`. A planned DynamoDB Local run submits each shape to confirm the API accepts it. A reviewer adding a transaction must add its row and this check.

### Service access and credentials

The memory API service is the only holder of backend data-plane credentials in each environment. Agents call it with signed service tokens over **HTTPS with authenticated TLS, which is required for every non-loopback connection to the memory service in every environment, including private networks**; plain HTTP is allowed only to loopback (127.0.0.0/8, `::1`) for local development and tests. This is deliberately stricter than the general credential rule in `AGENTS.md` (which also permits HTTP to a literal private IP) because memory carries content, and it does not change `AGENTS.md`. A client whose configured memory-service URL is `http://` and non-loopback must refuse to start. Tokens and memory content therefore never cross a private network in clear text, so no AWS or DigitalOcean store credentials spread to agents, authorization lives in one place, and no database is exposed publicly. The service becomes the memory trust anchor and a single point of failure, so it must be hardened and audited. Under the environment placement decision, Production's service fronts the AWS backend and Stage's fronts the Stage backend; the two do not share credentials or data. Where each service itself runs (for example, whether Production's runs on AWS with a local identity to DynamoDB, or elsewhere with a stored key or federated identity) remains a founder decision.

## Alternatives considered

Direct data-plane access from each agent (spreads AWS keys, repeats authorization everywhere, no clean rotation); AgentCore Memory as the single store; a vector database first; keeping local files (no sharing, ephemeral on DigitalOcean), and a single AWS store for every environment (superseded by the environment placement decision), and DynamoDB for Production with a different engine behind the same interface for Stage and local (rejected by the 2026-11-10 amendment because the guard rules and interleaving tests would be implemented and verified twice, and Stage's guarantees could be weaker).

## Consequences

A new service and a PostgreSQL database in each environment to operate and pay for; one implementation to verify in every environment. Bodies in the row remove the S3 protocol but cap practical body size; a large-body need would reintroduce object storage. Recall is by key and tag until semantic search is justified. Existing `remember()` callers must move to the service or stay as non-authoritative local logs.

## Test plan (no live inference; a local PostgreSQL container and fixtures)

The same contract tests run against the local PostgreSQL container and, before each is adopted, against the Stage and Production instances (originally DynamoDB Local for Production). The transaction-shape check above.
