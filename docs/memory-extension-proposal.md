# Proposal: extending governed memory beyond Charlie (not decided, not implemented)

Status: PROPOSAL for founder review. This is not an ADR and changes no behavior. Today only Charlie
(the synthesis service) uses governed memory, in the agent-private tier, as ADR-009 and
`docs/memory-service.md` describe. The code is the authority: `charlie_memory.py`,
`memory_client.py`, `execution_config/memory_policy.toml`. Part of #40; nothing here is to be built
before Stage launch of Charlie's memory is verified.

## Why consider it

Charlie's memory records only counts and enumerated labels about its own earlier syntheses. Other
agents could, later, avoid repeating work or keep per-agent notes. That value is unproven. The
proposal exists so the decision is made deliberately, with the controls below, rather than by adding
a client to another service. Extension is optional; "no" is a valid outcome.

## What exists today that this builds on

- The memory service enforces: a signed ADR-006 A2 assertion, a key in the memory registry bound to
  one `sub` with `memory.read` / `memory.write`, then a policy-table entry for that `sub`, and a
  scope that equals the caller's own `agent_id`. All three are required.
- The policy file already names nova, scout, cipher, charlie, pixel and sage with agent-private and
  session operations (charlie: agent-private only). Being named is necessary, not sufficient: no
  shipped registry gives any other agent a memory key, no Compose or Stage service other than
  synthesis has a memory URL, and `load_client` returns nothing for any agent kind but `synthesis`.
  Tests in `tests/test_runtime_memory_isolation.py` pin all of this.
- A content-free, best-effort client: bounded total deadline, one retry for writes with a derived
  idempotency key, fixed reason codes, memory text shown to a model only inside an untrusted block.

## Contract (unchanged, reused per agent)

Each agent would use the same REST contract at `/memory/agent/<agent_id>/records`, with its own
signing key and `sub`, its own `memory_policy.toml` entry, and its own scope. No shared scope, no
cross-agent reads. A model never decides whether memory is read or written: the application does,
before and after the model call, and every failure degrades to no memory with one log line.

## Namespaces and tags

One tag per agent and schema, for example `research-meta`, `fact-check-meta`, `privacy-review-meta`,
mirroring Charlie's `synthesis-meta`. The record body is a fixed, versioned JSON schema of counts and
enumerations defined in code per agent (like `charlie.synthesis.meta/1`). Free text from a question,
a source, a response or a document is never stored in the first phase. Session scope stays unused
until a concrete need exists. Engagement-shared (`/memory/eng`) and institutional tiers remain
reserved.

## Policy changes required (each a reviewed repository change)

1. A per-agent client module or a generalization of `charlie_memory.py` with the agent's schema
   and its own `load_client` branch (today a hard-coded `synthesis` check).
2. A memory registry entry per agent (key, `sub`, capabilities), generated by the dev script and,
   for Stage, by the founder through the memory service launcher; nothing generated in source.
3. Trim `memory_policy.toml` so each integrated agent gets only what it uses (for example
   agent-private read and create, `session = []`), and so agents not integrated have no entry or no
   operations. Today nova, scout, cipher, pixel and sage hold the full set though unused; that is
   latent and gated by the registry, but tightening it before extension is cheap and safer.
4. Per-agent classification ceiling stays `internal`, `allow_personal_data` stays false.
5. Founder approval, because policy, registry and the documents that describe them change.

## Risks

- Prompt injection through stored text: mitigated only while records hold counts and enums. Storing
  summaries would reintroduce the risk and needs its own review (delimiting, size, provenance).
- Privacy: Cipher and Scout see sensitive material. Their memory must never hold content derived
  from it; erasure and retention (placeholders today) must be decided first.
- Coupling and availability: each integrated agent gains a soft dependency. The best-effort client
  and bounded deadline keep it soft; the total latency budget is paid per request and per agent.
- Cost and storage growth: records per request per agent. Retention limits and the 90-day default
  apply; volume estimates are unverified.
- Independent deployability: every agent keeps its own configuration. No agent may require memory
  to start or to answer. Stage services must not gain memory settings until each is approved.
- Confused deputy: a runtime that shares a key between agents would break scope. One key per `sub`.

## Test plan

For each agent added: the Charlie test set repeated for that agent (read before model, write after,
failed model writes nothing, 401/403/503/down/TLS failure each give an ordinary answer and one
content-free line, retries and idempotency, signed with the right `sub` and capability, no content in
logs). Plus negative tests that must keep passing: every agent not yet integrated makes zero memory
requests with a URL configured, only integrated services carry memory settings in Compose and Stage,
registries name only approved subs, the policy snapshot test is updated deliberately in the same
change, and cross-agent scope access is refused (403). Live checks stay opt-in.

## Open questions for the founder

Which agents, if any; whether Stage should host memory for them; retention and erasure policy; whether
any non-metadata content may ever be stored.

# Stage smoke-test plan for the runtime (PLAN ONLY: nothing below has been executed)

To run after an approved promotion of a specific build to Stage. Check, record the result and the
build identifier, and stop at the first failure. None of this was run while writing this plan.

1. Deployment status: the provider shows the web service and the six agents (research, security,
   fact-check, source-quality, privacy-review, synthesis) active on the intended commit; no pixel or
   sage component. Confirm `deploy_on_push` is still disabled.
2. Health: `GET /health` on the web service returns ok. Each agent's health check in the provider is
   passing; specialists report their own `agent` name. Confirm health stays ok if memory is absent.
3. Configuration sanity: only the synthesis service has memory settings (and only if memory is
   provisioned); the other five have none. `LITELLM_BASE_URL` and keys are set as secrets, none in
   the spec.
4. Routing: one benign chat question reaches research, then fact-check, source-quality, privacy-review
   and security as the plan requires, and synthesis answers. Request IDs correlate across web and
   agents in the logs.
5. Streaming: the live stream delivers incremental events and a terminal event; closing the browser
   mid-stream does not leave a stuck run.
6. Error propagation: with one agent made unavailable by the operator (not by editing source), the
   user gets a clear, bounded error, no stack trace or prompt text, and other agents stay healthy.
7. Degraded memory (only if memory is provisioned): with memory stopped, a question is still
   answered normally; logs show exactly one content-free `read` and one `write` line with a reason
   code per request, and no question or answer text.
8. Memory enabled (only if provisioned): a second question shows a `read` record count above zero and
   a `write` ok; stored content is counts and labels only (verify through the memory service's
   own audit, not by copying records elsewhere).
9. Isolation: logs show no memory activity from any agent other than synthesis; the memory service
   refuses a non-synthesis caller if the operator probes it with a test key.
10. Inference path: model calls appear only through the LiteLLM endpoint; no provider-native traffic.
11. Logs and cost: structured JSON logs carry agent, request ID, destination, alias and duration, with
    no prompts or secrets; compare cost indicators with the promotion summary.
12. Rollback readiness: the previous build identifier is known and the rollback step is stated
    before promotion.

Report after the run: whether it ran, what happened, whether it succeeded, and the provider's
deployment status and health result (AGENTS.md).
