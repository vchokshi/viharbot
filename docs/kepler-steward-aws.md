# Kepler: first-contributor steward on AWS AgentCore (design)

Status: **AWS foundation provisioned; the agent is not built or deployed.** Tracking issue [#198](https://github.com/vchokshi/viharbot/issues/198) is the source of truth. It supersedes the autonomous coding mission in #125 and #127 to #131 (see [Kepler](kepler.md) for that history, which is preserved). Merging or reverting this PR does not change AWS: the IAM objects and foundation resources listed in [aws-lab-change-record.md](aws-lab-change-record.md) already exist in the lab account, and AWS teardown is a separate action (see Rollback). There is **no runtime, no schedule, no alert-writer, no secrets, and no application code** for the steward yet, so everything described below as behavior of the agent is proposed.

**Permanent constraint:** ViharBot does not deploy or operate unsupervised coding agents. Kepler never writes source code, pushes commits or branches, approves or merges pull requests, deploys, changes repository security settings, or grants itself permissions.

## What Kepler does

It watches for first-time contributors and their open pull requests, works out the onboarding steps still outstanding (CLA acceptance and its record, third-party rights disclosure, commit identity, branch freshness, CI and review state), tracks replies and new commits, drafts respectful follow-ups, and alerts the founder. First case: PR #179. Initial mode is **read-only monitoring plus internal alerts**. Contributor-facing text is drafted only and needs founder approval to post.

Status facts come from the GitHub API and the trusted-base `CLA-ACCEPTANCES.md`, by deterministic code, never from a model and never from an unverified comment. PR bodies, comments, commits and repository files are untrusted data and are never treated as instructions.

**The model writes no text a contributor reads.** Drafts are fixed templates filled with the contributor's GitHub login, the legal-terms version and the exact acceptance statement from the CLA gate. For a first-contact welcome draft a model **picks one category** (docs, bugfix, tests and so on) for the pull request, and the opening sentence is the approved sentence stored under that category. It never writes the AI introduction, the CLA statement, any request or the closing disclaimer. The model is **on by default** (the founder confirmed on 2026-11-07 that Kepler will make model calls), `KEPLER_MODEL_ID=off` turns it off, it is used for drafting only, and a human reads and posts everything. See "Operator contract" and "Model-assisted drafting" below.

### Assessment core (built, offline; not deployed)

`src/viharbot/steward/` is a pure, read-only core with no AWS and no network of its own. It reuses the repository's own CLA gate (`.github/scripts/cla_gate.py`) by loading and calling it, so Kepler cannot disagree with the merge check about who is covered, and every verdict records a fingerprint of the gate code that produced it. The gate must be present in the runtime image; if it cannot be loaded the steward reports "cannot conclude" and never guesses.

For one pull request it reports six requirements, each `done`, `outstanding`, `needs_human` or `info`: CLA acceptance recorded, third-party rights disclosure, commit identities linked to accounts, branch up to date, automated checks, and human review. It never marks the CLA done from a comment: a valid, unedited acceptance comment from the author is reported as "claimed, awaiting the founder to verify and record it". A reply from the contributor, or CI waiting for the founder to approve a fork's workflows, is `needs_human`, because only the founder can judge them.

Each outstanding or needs-human requirement gets an observation ID built from the repository, PR number, requirement, status and, only where it depends on it, the head commit. The same facts always give the same ID (so a re-poll or a duplicate event never re-alerts), a new push changes the CI, branch and identity IDs but not the CLA one, and a changed status gives a new ID. The drafter never repeats a CLA request that is still fresh (72 hours), sends a reminder listing only what is still outstanding, and produces nothing when the contributor has already replied.

Nothing a contributor writes reaches an assessment, an alert or a draft; only GitHub account logins, which GitHub restricts to letters, digits and hyphens, can surface. GitHub is read through GET requests only.

### Orchestration (built, offline; not deployed)

`poller.run_poll` runs one poll: authenticate, read the CLA record from the base branch pinned to one commit, sweep open first-time PRs (bounded), assess each, and email the founder about what is new. Its rules, all covered by tests:

- **Authentication.** `github_auth` is the only module that sends a non-GET request, and only the token exchange for the reader's own installation. It **refuses a token whose permissions are not exactly the reader's read-only set**, or that reaches more than the one repository, and never uses it. Keys and tokens never appear in an error, a log or a record.
- **Deduplication.** An observation is claimed with a conditional write (`pending`), the email is published, then it is marked `sent`. The runtime may not delete rows, so a claim is never released: a stale `pending` claim can be retaken after 30 minutes, at most `KEPLER_MAX_ALERT_ATTEMPTS - 1` times (default 2 attempts, so one retry). The honest guarantee is **at-least-once with a bounded duplicate count**: if polls keep dying between publishing and marking, each death can cost one duplicate until the budget is spent. Then the observation becomes `exhausted`, is reported once (`alert_exhausted` audit event, `AlertsAbandoned` metric, run `partial`) and is never sent again. A restart, a repeated poll or a duplicate GitHub event sends nothing.
- **Fail closed.** If the state table or the audit log cannot be written before an email, the run stops and sends nothing, because without them there is no dedup and no record. The `alert_intent` event is audited before publishing. If the audit store fails after the email has gone, the email cannot be unsent: the intent has no outcome event, and `uncertain_intents` lists it for reconciliation. An auth, base-read or listing failure also fails the run. One bad pull request does not stop the others: it is audited and the run is `partial`.
- **Bounded.** No GitHub read, claim or email starts after the deadline (default 240 s; reads stop 15 s earlier to leave time to record the end). The worst overrun is one GitHub read already in flight, about 45 s with the configured attempts and rate-limit wait. A run reads at most 25 pull requests, and a metrics outage never fails a poll.
- **Visible.** `PollCompleted` is the heartbeat metric (0 on a failed run), `PollFailed` is 1 unless every step succeeded, and `PRsAssessed` and `AlertsSent` are counts. Logs are JSON with `agent`, `request_id`, `event`, `destination`, `model_alias` (always null: no model), `duration_ms` and `error_code`.
- **Audited.** Every run writes hash-chained events (`poll_started`, `alert_sent` with the gate fingerprint, `pr_failed`, `deadline_reached`, `poll_completed`) to the audit table. The writer refuses unknown fields and any value that is not short and plain, so a contributor's text, a token or a stack trace cannot be recorded by accident. The chain is tamper-evidence, not tamper-proofing (see the audit caveat above).
- **Email.** Fixed wording only: the PR link, the author's login (validated), what is new, where each requirement stands, recommended actions, and a draft clearly marked NOT posted. A single poll sends at most one email per PR.
- **Dry run.** `python -m viharbot.steward [--pr N]` reads and assesses with the reader app and prints what would be emailed, writing nothing (no state, audit row, email or GitHub comment). It is the local proof that the GitHub side works. A live run belongs to the deployed runtime.

AWS is imported in exactly one module (`aws.py`); everything else takes injected clients, which is how the tests run offline against fakes that implement DynamoDB's real conditional-write behaviour.

### Runtime adapter and image (built; not deployed)

`runtime.py` serves the AgentCore contract: `GET /ping` and `POST /invocations`. It is standalone (it does not import another agent's adapter, so the steward stays independently deployable). Input is a strict schema with two actions: `poll` (what the schedule sends) and `check` with one pull request number ("check now"); anything else is refused with 422 before any work, an oversized body with 413. Each action takes an optional `wait` flag (a strict boolean, default `true`): `false` starts the poll in the background and returns `202 {"status":"accepted"}` at once, which is how the schedule calls it (see "Scheduler" below); the outcome then shows in the heartbeat metrics, the audit log and the alert email rather than in the response. `GET /ping` reports `HealthyBusy` while a poll runs, foreground or background (AgentCore keeps a session alive past its idle timeout only while it reports that), and `Healthy` otherwise. One poll runs at a time per container (a second gets 409; the database guards across containers). The response is counts and codes only, never an email body. A crash returns a fixed 500 body, tells the failure alarm, and leaks nothing. An invalid configuration stops the service from starting (a `--factory` start), so a misconfigured container is never "healthy", and neither startup nor `/ping` contacts AWS. AgentCore authenticates callers before a request reaches the container, so the service has no authentication of its own and must never be exposed beyond AgentCore; a local run binds loopback.

`Dockerfile.kepler` builds a linux/arm64 image (the build fails loudly on any other target). It is deliberately minimal: four pinned direct dependencies (`requirements-kepler.txt`: fastapi, uvicorn, boto3, cryptography) and **no model SDK**, only the steward's own source, the request limiter and the two CLA-gate files (an allowlist in `Dockerfile.kepler.dockerignore`, so no `.env`, credentials, `.git` or docs), an unprivileged user, a health check, and no secret: the GitHub App credentials are read from Secrets Manager at run time. `deploy/agentcore/kepler/smoke-test.sh` builds it and runs it the way AgentCore would (no credentials, read-only filesystem, no capabilities, loopback only); 29 checks passed when last run (the count is a local report, not CI evidence), including a bad configuration refusing to start, strict input, a poll with no credentials failing closed without leaking, and no model SDK, secret or `.env` in the image. The image is about 313 MB, larger than a bare Python image mostly because of boto3.

### Introducing Kepler, and saying it is an agent

Every message Kepler drafts says plainly that it comes from an AI agent, so a contributor never has to wonder whether they are talking to a person. The first message also introduces Kepler as **the first of ViharBot's agents the contributor will interact with, and says there are more**; says what it does (welcomes first-time contributors and helps with the contribution paperwork) and what it cannot do (change code, merge, or decide whether a contribution is accepted); and offers a person on request. It says truthfully who posts it: today the maintainer reads the draft and posts it, so the message says "drafted by me and reviewed and posted by @maintainer"; a later phase in which Kepler posts approved messages itself says "approved by @maintainer and posted by me". A reminder carries a short signature and does not repeat the introduction. The maintainer's login comes from the registry on the base branch and is validated before it is written into a message.

**Open item:** the Kepler identity files (`src/viharbot/agent_identities/kepler.toml` and its prompt) still describe the superseded autonomous coding agent. They need a human-reviewed update to the steward role (a governance change, not made here).

**Not yet built:** the IAM change that lets the runtime publish to the alerts topic (`sns:Publish`, a new boundary version and a runtime policy change; until it is applied the runtime role cannot send the email), the heartbeat alarm, pushing the image and creating the runtime. The scheduler role and 6-hour schedule are written as files and a dry-run-by-default script but **not applied** (next section).

### Scheduler (built as files; not applied; needs a deployed runtime)

AgentCore Runtime is invoked, not scheduled, so EventBridge Scheduler calls it. `deploy/agentcore/kepler/iam/scheduler-trust.json` and `scheduler-policy.json` define the role `viharbot-kepler-scheduler`: only EventBridge Scheduler can assume it, only for `viharbot-kepler-*` schedules in this account (`aws:SourceAccount` and `aws:SourceArn`), and its one permission is `bedrock-agentcore:InvokeAgentRuntime` on the one Kepler runtime, inside the existing permissions boundary. `build_schedule.py` builds the `CreateSchedule` request, and `create-schedule.sh` is a **dry run unless `APPLY=yes`**, run by the administrator only after you approve and only once the runtime exists. Tests check the request against the AWS SDK's service model and check that the runtime accepts exactly the payload the schedule sends.

- **Two stages.** `test` creates a one-time schedule three minutes out that deletes itself, to prove the whole path. `recurring` creates `rate(6 hours)` **DISABLED**, and you enable it after the test passed. A manual check-now is a direct `InvokeAgentRuntime` call with `{"action":"check","pr":N}`.
- **Why `wait: false`.** Scheduler calls a universal target synchronously and has been observed giving up on slow calls at about 30 seconds (an observed figure in two third-party write-ups, not an AWS-documented limit), while a poll can take up to 240 seconds. A synchronous call would be recorded as a failure even when the poll succeeded, and a retry could start a duplicate poll. So the schedule asks for the background form and has retries off; the next run is the retry. AgentCore's own guidance for long work is the same pattern: return at once, report `HealthyBusy` on `/ping` while working. AgentCore's maximum session lifetime and maximum synchronous request time were not found in the pages read, so check them before the first deploy.
- **Unverified, to be settled by the `test` run.** The universal-target name `bedrockagentcore` is inferred from the SDK service id, not from AWS documentation. Whether the target takes `Payload` as plain JSON or base64 is unknown (`PAYLOAD_ENCODING=base64` is the fallback). Whether `bedrock-agentcore:InvokeAgentRuntime` needs the `runtime-endpoint` resource is covered by granting both, which is unconfirmed. If the path cannot be made to work, the fallback is a small Lambda that calls `invoke_agent_runtime` with the same payload.
- **Gaps recorded, not hidden.** EventBridge Scheduler schedules cannot carry tags (`CreateSchedule` has no tags field; `TagResource` is for schedule groups), so the schedule is identified by its `viharbot-kepler-` name, the role is tagged, and the cost is per invocation, about four a day. The deployer policy's `scheduler:TagResource` on schedules has no effect. `InvokeAgentRuntime` is a CloudTrail data event, off by default, so there is no audit trail of invocations until data events are enabled. A failed or dropped invocation is not alarmed yet: the heartbeat alarm (the `PollCompleted` metric missing for 7 hours) is the planned catch-all.

## Inference

**Decision: Kepler calls Amazon Bedrock directly, authorized only by its IAM execution role, with no API key and no LiteLLM.** This is the scoped exception to the repository's LiteLLM-only rule that the founder accepted in ADR-011 (`docs/adr/ADR-011-kepler-inference-exception.md` on `main`, 2026-11-05) and wrote into `AGENTS.md`; the founder chose Meta Llama, and on 2026-11-06 chose drafting-only use. It applies to the Kepler steward only; every other agent keeps the LiteLLM rule, and no agent acts autonomously. The IAM change that allows it was applied on 2026-11-06 (change record row 12; boundary version 3 and the runtime role policy, simulation 41 of 41), so the runtime role can now call that one model and no other. No model call has been made yet, and Bedrock price in the account is unverified. The code uses the model by default, so the first live call will happen the first time a deployed Kepler is about to send a first-contact welcome email; `KEPLER_MODEL_ID=off` prevents it.

- **One approved model:** `meta.llama3-1-8b-instruct-v1:0` in `us-west-2`, on-demand and in-region (the account is already `AUTHORIZED` for it). I chose the small 8B model because the task is picking one word from a fixed list; the larger Llama 3.3 70B runs only through a cross-region profile, which would send contributor text through other regions. The choice is one config value (`KEPLER_MODEL_ID`) and one IAM resource ARN.
- **Enforced three ways, kept in sync:** ADR-011 requires an explicit allowlist that fails closed, so the configuration (`APPROVED_MODEL_IDS`) refuses any model id that is not exactly `meta.llama3-1-8b-instruct-v1:0` (no other Llama, no `us.` or `global.` profile, no other provider, so never an Anthropic model); the client refuses to be built for anything else; and the IAM policy allows `bedrock:InvokeModel` on that one ARN, explicitly denies every other model and every Anthropic model or inference profile, and a test fails if the code's allowlist and the policy's ARN ever differ. The deployer role keeps its blanket deny, since it never invokes a model.
- **On by default, with a kill switch.** No setting is needed: Kepler uses the approved model unless told otherwise. `KEPLER_MODEL_ID` is an override that must still be the approved id (anything else stops startup), and `KEPLER_MODEL_ID=off` (or `none`, `disabled`) turns the model off so drafts are the plain template. An empty value means the default, not off. A dry run never calls a model.
- **No key:** the runtime role's credentials are the only authorization, so there is no LiteLLM secret, no gateway CA in the image, and no long-lived credential to leak.
- **Invocation logging.** Bedrock model invocation logging appears unconfigured in this account today. If an administrator enables it so the calls are visible to monitoring, the log records prompts and replies, which here contain a sanitized pull request title and file paths (not the login) and a one-word category, so choose its retention and access deliberately.
- **Cost** is Bedrock on-demand pricing for a tiny prompt (the reply is one word, capped at 150 tokens) once per first-contact email; it is not tagged per call, and the price in this account is unverified.

**Operator contract (one place).** *Default:* on, with no setting needed; the approved model only. *Kill switch:* `KEPLER_MODEL_ID=off` (also `none`, `disabled`); empty means the default, not off; any other id stops startup. *Data sent, once per first-contact welcome email and never in a dry run or a test:* a cleaned pull request title (100 characters) and up to five cleaned file paths inside an untrusted `<data>` block, nothing else. *Data returned:* one category key; a reply that does not name exactly one key is discarded and the plain template is used (the only leniency is cosmetic: case, surrounding whitespace, one layer of quotes or backticks and one trailing `.`, `,` or `!`, and the result is still a lookup, so no model text survives). *Time:* the whole call, retries and reading the reply included, is hard-capped at 20 s of wall-clock time and then abandoned (its background thread finishes on its own and the result is discarded); inside that, each attempt uses 3 s connect and 10 s read socket timeouts with two attempts in total (socket timeouts alone are not a wall-clock guarantee); and the call is skipped when under 30 s of the poll's budget remain. *Concurrency:* at most one model call is in flight per process; a call abandoned at the cap keeps that slot until it really ends, and meanwhile later drafts use the plain template (code `busy`), so repeated timeouts cannot pile up threads, connections or overlapping billable requests. *Cost:* as above. The first live call happens the first time a deployed Kepler is about to send such an email.

### Model-assisted drafting (built; on by default once deployed; not deployed yet)

One call per first-contact welcome draft, made only when an email is about to be sent (not on every poll, not for reminders, never in a dry run). What reaches the model is deliberately small: the pull request title reduced to plain words (markup, links, mentions and tags removed, 100 characters) and up to five cleaned file paths, inside a `<data>` block the prompt declares untrusted. The contributor's login, any comment, PR body, profile text or email address, and the CLA text are not sent. The model has no tools and cannot act.

The model chooses; it does not write. Its reply is accepted only if it names exactly one key from a fixed table of eight approved openings (`OPENINGS` in `personalize.py`), and the contributor sees the approved sentence under that key. Anything else, any model error, any timeout and a poll short of time means the draft is simply the plain template, and a model problem never fails a poll. The promise-free, request-free, legal-free, link-free and "not open source" properties therefore rest on **a person approving every sentence in the table**, not on a guess about model prose. An automated lint also runs on the table at import and in tests, but it is a regression aid and not a semantic guarantee: it rejects known patterns (for example "we expect to merge this next week" and "please send your password") and can miss an indirect commitment ("we expect to merge your contribution" passes it, and a test records that limitation). Adding a category means a person writes one sentence, and it needs human review in the pull request that adds it. The audit log records a `draft_model` event with only the model id, whether it was used or rejected, and a fixed reason code (`not_a_choice`, `empty`, `model_error`, `timeout`, `busy`, `no_budget`), never the prompt or the reply.

**Not yet built:** reading and summarizing a contributor's reply, and conversational drafts. Those widen the untrusted input and need their own design and your decision. Nothing posts autonomously at any stage.

## Roles and how they are created

1. **You, as administrator, once:** create the permissions-boundary policy `viharbot-kepler-boundary` and the role `viharbot-kepler-deployer` (trust and permissions in `deploy/agentcore/kepler/iam/`). The deployer cannot create or change the boundary, which is why this step is yours.
2. **The deployer role, from then on:** creates everything else. It can create or manage only four explicitly named workload roles (`viharbot-kepler-runtime`, `-scheduler`, `-alert-writer`, and `viharbot-kepler-test-*` for authorization tests), and only with the boundary attached. It can pass only the first three, only to AgentCore, Scheduler and Lambda. It is explicitly denied every change to its own role, including its trust policy, tags, permissions and deletion, and it cannot remove the boundary, create users or keys, or touch other accounts' resources. It cannot rewrite a workload role's trust policy, and it has no resource-policy powers (no `PutResourcePolicy` on secrets, `SetRepositoryPolicy` on ECR, or `AddPermission` on Lambda), so it cannot expose a secret, image or function to another principal. It can create the audit table but is denied altering, restoring or deleting it, so only the administrator can. The first version used a `viharbot-kepler-*` wildcard that also matched the deployer; the external Sage review found that, and the founder's IAM review found the rest. All are fixed (see change record).
3. **`viharbot-kepler-runtime`:** the AgentCore execution role. Pull its own image, write logs, put metrics in its own namespace, read two secrets, use the state and audit tables as described above, and invoke the Phase 2 comment-writer function (that permission already exists but there is no function yet). It does **not yet** have `sns:Publish` on the alerts topic, which it will need to send email; that administrator change, with a new boundary version, comes with the runtime build. Denied: deleting anything in DynamoDB, altering the audit table, reading the alert-writer secret, invoking any foundation model other than the one allowlisted non-Anthropic model (every Anthropic model is denied).

**Boundary.** `viharbot-kepler-boundary` (version 3) is a ceiling on every role the deployer creates, and it is **resource-scoped**: Kepler secrets (`viharbot/kepler/*`), tables (`viharbot-kepler-*`), the one ECR repository, Kepler functions, Kepler and AgentCore log groups, its own metrics namespace, and AgentCore runtimes in this account. Version 1 allowed the same actions on `*`, which a simulation showed would let a bounded role with a broad policy attached read any secret or table in the account. A simulation of an all-allow identity policy capped by version 2 now reaches only Kepler's resources, and IAM, Organizations, role assumption and model invocation beyond the one allowlisted non-Anthropic model are explicitly denied. Resource ARNs use a wildcard region segment and are scoped by account and name prefix, so agents deployed in other regions fall inside the same boundary.

**Region guard (deferred, by decision).** There is no policy that denies actions outside `us-west-2`. The founder expects agents to run in different regions for reliability and redundancy, so a hard region lock would fight that. The deployer policy's resource ARNs name `us-west-2` today and will be extended per region; the boundary is already region-agnostic. Revisit a region allowlist once the set of regions is known.

The policies passed IAM Access Analyzer validation with no findings (syntax and action names only; that does not prove sufficiency). Validation caught three mistakes in my first draft, and the Sage review plus live probes found three further authorization gaps, all recorded and fixed. Authorization tests are in `deploy/agentcore/kepler/iam/tests/`: `deployer-negative-test.sh` (27 live checks as the deployer role) and `policy-simulation.sh` (36 read-only simulator checks of the boundary, deployer and runtime role). One thing the simulator cannot show: for CloudWatch Logs it evaluates the log group (`NAME:*`), never a log-stream ARN, so whether the runtime's log writes work is proven only by its first real run.

## Network boundary

Two options, and a decision is needed. AgentCore supports `PUBLIC` and `VPC` network modes.
- **Start `PUBLIC`, restrict in code:** no NAT cost. The runtime only ever connects to `api.github.com` (the GitHub client is fixed to that host) and to AWS service endpoints (Secrets Manager, DynamoDB, SNS, CloudWatch and Bedrock Runtime) through the AWS SDK. This does **not** restrict egress at the network layer, so a bug or a compromised dependency could reach elsewhere.
- **`VPC`, egress on 443 only:** a security group allowing only outbound 443, private subnets and a NAT gateway (a recurring charge). A security group cannot filter by domain; domain filtering needs DNS Firewall or Network Firewall, at more cost.

I recommend `PUBLIC` plus the code allowlist for the lab, with the limitation recorded, and `VPC` when the agent gets any write capability.
